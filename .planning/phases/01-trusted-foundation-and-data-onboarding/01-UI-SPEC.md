# Phase 1 — UI Design Contract

> Visual and interaction contract for Trusted Foundation and Data Onboarding. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

The phase improves the existing Chezcar prototype; it does not redesign the application. The only new user-facing surfaces are fixed-role/location access feedback, Admin User Management, and the first-login temporary-password prompt. Workbook profiling, ambiguity review, canonical seed generation, and reset/reload remain developer-operated and have no application upload or import UI.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | shadcn (`base-nova`, already initialized) |
| Preset | `base-nova`; neutral base, subtle menu accent, CSS variables, RSC enabled, LTR |
| Component library | Existing shadcn-style Base UI primitives in `components/ui/`; retain Radix only where already used |
| Icon library | Lucide React; 16px inline, 20–24px for standalone state icons |
| Font | Geist Sans through `--font-sans` |

### Existing assets to reuse

- Keep `AppLayoutShell`, `AppSidebar`, `AppHeader`, and `PageShell` as the application frame. Preserve the pinned desktop sidebar, mobile drawer, theme toggle, and current responsive padding.
- Use the existing `Button`, `Badge`, `Card`, `Dialog`, `Input`, `Label`, `Select`, `Table`, and `Sheet` primitives before creating any phase-specific presentation component.
- Use semantic CSS variables and the existing `brand` green scale. Every state must work in both the existing light and class-based dark themes.
- Use the Base UI `Select` for rewritten User Management fields; do not reproduce the prototype's hard-coded `react-select` color styles.
- Keep corners consistent with existing primitives: 10px base radius, 12px cards/dialogs, and up to 16px for prominent shell controls. Do not introduce a new radius language.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-label gaps and tightly related metadata |
| sm | 8px | Form label gaps, compact controls, inline actions |
| md | 16px | Default grid gaps, dialog sections, table controls |
| lg | 24px | Card padding and separation between page sections |
| xl | 32px | Desktop page gutters and major layout gaps |
| 2xl | 48px | Empty/access-denied state breathing room |
| 3xl | 64px | Reserved page-level separation; do not stack inside forms |

Exceptions: interactive controls must be at least 44px high or have a 44×44px hit area on touch layouts. Table rows may be 48px high. Preserve the shell's existing 20px mobile and 32px desktop page padding.

## Typography

Use exactly these four sizes and two weights on Phase 1 surfaces. Existing shell typography outside the touched surfaces is not restyled.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px | 400 | 1.5 |
| Label / metadata | 12px | 600 | 1.4 |
| Section heading | 16px | 600 | 1.25 |
| Page display | 24px | 600 | 1.2 |

- Labels use sentence case. Table headers may use uppercase with existing restrained letter spacing.
- Names, emails, branch names, and error text wrap rather than shrink below 12px. Identifiers may truncate only when their full value is available as accessible text/title.

## Color

The percentages describe visual area, not component counts. Semantic variables are authoritative in implementation; the hex values identify the existing light-theme intent.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#FBFEFC` / `--background` | Page background and ungrouped canvas |
| Secondary (30%) | `#FFFFFF` / `--card`, `--sidebar`, `--muted` | Cards, sidebar, dialogs, table headers, filter bar, neutral badges |
| Accent (10%) | `#17864A` / `brand-600`, `--primary` | Primary CTA, selected navigation, focus ring, active status, success feedback |
| Destructive | `#DC2626` intent / `--destructive` | Deactivate confirmation, destructive text, invalid fields, load/submit failure only |

Accent reserved for: `Create User`, `Change Password`, the selected sidebar item, keyboard focus rings, Active badges, successful mutation feedback, and the access-denied page's non-destructive dashboard link. Do not color every button, icon, table row, or section heading green.

- Dark mode uses the existing `.dark` semantic tokens; never retain light-only `slate-*` or white backgrounds without a dark counterpart.
- Inactive is neutral by default (`muted`); red is reserved for the deactivate action and blocking errors, not for every inactive badge.
- Never communicate role, status, validation, or access outcome by color alone; pair color with text and, where useful, a Lucide icon.

## Phase Surfaces

### 1. Role-aware application shell

- Sidebar navigation contains only pages allowed by the signed-in user's persisted role. `User Management` is visible to `ADMIN` only; remove `Users & Roles` and do not show `Manage Roles` anywhere.
- Menu visibility is presentation feedback only. Direct page and API requests remain independently server-authorized.
- Scope feedback is explicit near location-sensitive page controls:
  - Admin: enabled selector with `All locations` plus `Stock Room (SR)`, `QC`, `BL`, `LU`, `VC`, and `SP`.
  - Stock Staff: static/read-only `Stock Room (SR)` scope; no branch assignment control.
  - Branch Staff: static/read-only assigned branch code and name; no `All` option.
  - Accounting Staff: static/read-only `Business-wide` scope; this is not a location assignment.
- Never briefly render forbidden menu entries or protected content while session/capability data loads. Use the authenticated server-derived navigation state before rendering the menu.

### 2. Dedicated access-denied screen

- Render inside the authenticated Chezcar shell so the user retains theme, identity, and permitted navigation, but do not render the denied page header, filters, cached rows, or record identifiers.
- Center one restrained `Card` in the content region with a Lucide `ShieldX` icon, the fixed access-denied copy, and one `Back to Dashboard` button.
- A missing, expired, inactive, or revoked session goes to sign-in instead of this screen. A signed-in but unauthorized request goes here.
- Browser Back remains available; the only in-screen CTA goes to `/dashboard` and does not retry the forbidden route.

### 3. Admin User Management

Use `PageShell` at `/users`. The owner Admin may view all accounts but may mutate only non-Admin staff accounts.

**Page hierarchy**

1. `PageShell` header with the fixed title/subtitle and `Create User` action.
2. Three compact summary cards: `Total Staff`, `Active`, `Inactive`. The owner Admin is not counted as staff.
3. One filter card.
4. One user table card with result count, loading/update feedback, and pagination.

**Filters and pagination**

- Search name or email; filter by Role (`All roles`, the three creatable roles), Location (`All locations`, `SR`, five branches, `Not assigned`), and Status (`All statuses`, `Active`, `Inactive`).
- `Apply Filters` commits filter changes, resets to page 1, and preserves the complete applied state during pagination. `Reset Filters` clears all filters and returns to page 1.
- Use 10 rows per page and `Previous`/`Next` controls. Disable pagination during a page transition and retain prior rows with a subtle `Updating…` label; do not blank the table.

**Table contract**

- Columns: Name, Email, Role, Location Scope, Status, Last Sign-in, Actions. Do not show editable permissions or a permission count.
- Human labels are `Stock Staff`, `Branch Staff`, and `Accounting Staff`; do not expose enum formatting such as `BRANCH_STAFF`.
- Location cells read `Stock Room (SR)`, the assigned branch, or `Business-wide` as appropriate. Do not use `All Branches` for Accounting.
- Status uses text badges `Active` and `Inactive`. Unknown last sign-in renders `Never`, not a blank dash.
- Each staff row offers `Edit User`, `Reset Password`, and context-sensitive `Deactivate User` or `Reactivate User`. The owner Admin row is labeled `Owner Admin` and has no mutation actions.
- Keep a semantic table and horizontal overflow below its minimum readable width. The action group stays keyboard reachable and may wrap; do not collapse records into an unrelated visual card system in this phase.

### 4. Create and edit user dialogs

- Reuse `Dialog`; width is at most 672px, height at most 90vh, and body scrolls while header/footer remain understandable. On narrow screens use `calc(100vw - 32px)` and a single-column form.
- Create fields, in order: Full Name, Email Address, Role, Location Scope, Temporary Password, Confirm Temporary Password, Status. Default Status to `Active`.
- The Role selector contains only Stock Staff, Branch Staff, and Accounting Staff. `Admin` is never an option.
- Role/location behavior is immediate and deterministic:
  - Stock Staff sets a visible read-only location to `Stock Room (SR)`.
  - Branch Staff reveals a required branch selector containing exactly `QC`, `BL`, `LU`, `VC`, and `SP`.
  - Accounting Staff sets a visible read-only scope to `Business-wide` and submits no location assignment.
  - Changing role clears an incompatible prior location before submit.
- Temporary password fields are masked, support password managers, are never logged or echoed after success, and show the offline-handoff helper text before submit.
- Edit excludes temporary-password fields; credential reset is a separate dialog. When role or branch changes, show the fixed revocation warning directly above the footer.
- Validate on blur and submit. Put a specific message directly under each invalid field, set `aria-invalid`, focus the first invalid field after submit, and retain all entered values after server rejection.
- Footer order is secondary `Cancel`, then primary `Create User` or `Save Changes`. While submitting, disable duplicate submission and change the label to `Creating User…` or `Saving Changes…` with `Loader2`.

### 5. Lifecycle confirmations and feedback

- Deactivation requires a destructive confirmation dialog with user name, immediate sign-out consequence, secondary `Cancel`, and destructive `Deactivate User`.
- Reactivation requires a neutral confirmation dialog; it is not styled destructive.
- Reset Password uses two masked fields (`Temporary Password`, `Confirm Temporary Password`) and primary `Reset Password`. It never displays or generates a password in the browser.
- Successful mutations close the dialog, refresh the affected row and counts, preserve applied filters/page when valid, and announce the fixed success copy in a visible `role="status"` banner.
- Failed mutations keep the dialog open, preserve values, re-enable controls, and show a problem-plus-next-step message in `role="alert"`. Do not imply a durable change before the server response succeeds.

### 6. First-login temporary-password prompt

- After successful sign-in with a newly created/reset credential, show a blocking credential dialog before navigating to the requested business page. It contains Current Password, New Password, and Confirm New Password.
- Primary action is `Change Password`; secondary is `Skip for Now`. Skip continues to the safe callback destination without claiming the credential changed.
- Default behavior: the prompt is consumed after the first successful login attempt whether changed or skipped, and appears again after a later Admin credential reset.
- Password-change loading, field errors, and server failure follow the same form rules as User Management. Never expose password values in banners, URLs, logs, or page text.

## Responsive and Accessibility Contract

- Mobile-first breakpoints follow the existing Tailwind setup. Below `md`, forms and filters are one column; at `md` they may use two columns; desktop filters may use a compact multi-column row.
- Preserve the existing mobile sidebar drawer and 20px page padding. Dialogs remain fully operable at 320px CSS width without horizontal page scroll.
- Visible focus uses the semantic ring on every interactive element. Do not remove outlines. All icon-only controls have accessible names and a 44×44px touch target.
- Dialogs trap focus, close on Escape unless a mutation is in flight, return focus to their trigger, and use title/description associations from the existing primitive.
- Loading and updating labels use `aria-live="polite"`; validation/load failures use `role="alert"`; success messages use `role="status"`.
- Respect `prefers-reduced-motion`: no required information depends on zoom, slide, spinner motion, or a timed disappearance.
- Maintain at least 4.5:1 text contrast and 3:1 focus/control-boundary contrast in both themes.
