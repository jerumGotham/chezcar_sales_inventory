# Reports Production Spec

**Status:** Three focused reports in source; 2026-09-08 revision unverified at owner request
**Last updated:** 2026-09-08
**Source:** Owner Reports revision, 2026-09-08; ADR 0017 (supersedes ADR 0013)

## Purpose

Provide three concise, read-only reports from live persisted data: Sales, Inventory Summary, and Returns & Warranty. Inventory Movements and Low Stock are deferred from Reports for now. Operational inventory history, movement records, stock alerts, Accounting queues, and open Customer Orders remain in their own modules and are not removed or duplicated here.

## Access

- Reports require `reports:view`; PDF export additionally requires `reports:export`.
- Access is determined by capabilities, not built-in role names.
- Every query and export is limited to effective location access. Company-wide users may compare all authorized branches; branch-scoped users see only their branch.
- Sensitive cost fields require a separate cost-view capability if introduced.

## Global Rules

- Reports query the live database and do not save report snapshots or generated PDFs.
- Date-based reports default from the first through the last day of the current Asia/Manila month, not month-to-date. On 2026-09-08 this means `2026-09-01` through `2026-09-30`.
- The date labels are From / To. Small helper text identifies verification date for Sales and case creation date for Returns & Warranty. Both ends are inclusive Manila calendar dates; the database upper bound is the following Manila midnight, exclusive.
- An omitted To defaults to the last day of the supplied/default From month. While To remains automatic, changing From updates month-end; manually entering To (including an explicit URL end date) makes it custom and preserves it across later From/location edits. Clearing To restores the default on Apply. Reset restores the current month in draft state. No date presets are currently exposed.
- Inventory Summary is a current snapshot and does not use a historical date range.
- Every filter edit, including location and Reset Filters, remains pending until Apply Filters. Results, totals, URL filters, and PDF parameters continue using applied filters. Switching report tabs is navigation and loads that report's defaults immediately.
- Filter options load independently of report rows, keyed by draft report/location/product status. Location changes clear draft Salesperson; product-status changes clear draft category/brand. Options remain usable even when report rows fail or draft dates are invalid; loading/error/retry states are separate.
- UI tables may paginate, but summary totals must use the full filtered dataset and must never be calculated from a display limit.
- PDF export uses the same selected report, filters, totals, and effective location scope as the UI.
- PDF metadata includes Chezcar company text (no literal logo placeholder or embedded logo), report title, selected filters/date range and date basis, generated by display identity, and generated at.
- PDF is the report export format. CSV report export and saved schedules are deferred.
- The query contract is strict. A filter not supported by the selected report, an unknown parameter, or any duplicated query parameter is rejected rather than ignored or collapsed.

## Query And Export Boundary

- `GET /api/reports` requires `reports:view` for JSON. `format=pdf` requires `reports:export`; the route removes only `format` and executes the same report query before rendering the PDF.
- The service validates report-specific filters, resolves active options inside effective location access, rejects an unauthorized/inactive requested `locationId`, and computes rows and full totals from that narrowed scope.
- Inventory Summary further restricts scope and location options to active authorized `BRANCH` locations. Explicit Stock Room/warehouse requests return `403`; warehouse-only actors get an empty branch snapshot, not access to branches.
- `/api/reports/options` requires `reports:view`, uses the same strict query validation and scope, and returns only `{ data: { locations, defaultLocationId, salespersons, categories, brands } }`. `defaultLocationId` is the first eligible branch for Inventory Summary (or `null` when none); it is `null` for other reports. The UI sends draft type/location and inventory product status only, without dates or dependent selections. It does not fetch report rows or totals.
- For Inventory Summary, omitted `locationId` resolves server-side to one authorized active branch, ordered by name then ID. The current access context exposes no preference/home-branch field; the compatibility `User.locationId` is not consulted. Explicit `locationId=all` selects all authorized active branches; an actual branch ID selects only that branch. Empty/duplicate parameters are invalid, and no eligible branches means empty rows/scope, never widened access. Options, JSON, and PDF share this resolution, so the first report request cannot fetch All while the selector shows a default branch. Sales and Returns retain their existing omitted-location semantics.
- `type=inventory-movements` and `type=low-stock` return `400 INVALID_FILTERS` for JSON, PDF, and options requests. Removed movement/low-stock-specific filter parameters are unknown and rejected. Old Reports page links for retired types open clean default Sales filters; operational `/api/inventory/movements` is unchanged.
- JSON and PDF responses are private and not cached. Generated PDFs are not persisted.
- PDF includes report title, generated actor/time, effective locations, date basis, selected filters, the complete authorized rows, and the same summaries/breakdowns returned to the UI.
- All retained PDFs use A4 landscape, 9-point detail text, proportional column widths, wrapped cells/long identifiers, numeric alignment, alternating row shading, repeated section/table headers, and page numbers. Ordinary rows stay together when they fit a fresh page; oversized rows continue across pages without truncation. Sales and Returns detail fields are grouped into labeled multiline cells rather than tiny individual columns.
- PDFs rerun the live query with applied filters; data can change between viewing and exporting. Generated reports are not a frozen snapshot.

| Report | Supported filters | Date semantics |
| --- | --- | --- |
| Sales | `dateFrom`, `dateTo`, `locationId`, `salespersonId`, `source`, `paymentMethod` | `verifiedAt`; current Manila month by default |
| Inventory Summary | `locationId` (branch ID or explicit `all`), `search`, `category`, `brand`, `productStatus` | Current positive available stock; one authorized active branch by default; all product statuses by default; no date range |
| Returns & Warranty | `dateFrom`, `dateTo`, `locationId`, `caseType`, `status`, `resolution`, `entitySearch` | Case creation time exposed as `caseDate`; current Manila month by default |

## 1. Sales Report

The Sales Report is the monthly sales report by default; there is no separate Monthly Sales menu.

### Inclusion and Date Basis

- Include only `VERIFIED`, non-voided sales.
- Group and filter sales by the system verification timestamp.
- Exclude pending/unverified sales from official totals.
- Customer Orders appear only through their completed/posted final sale, not as open orders.

### Filters

- Verification date from/to.
- Authorized branch/location.
- Salesperson.
- Source: Direct Sale or Customer Order.
- Payment method.

### Summary

- Total verified sales.
- Transaction count.
- Units/items sold.
- Total discount.
- Average sale amount.
- Branch rows with transaction count, units sold, sales total, and percentage of authorized grand total.
- Grand total across selected branches.
- PDF has a separate Branch Subtotals table with transaction count, units, sales amount, and share, ending in an emphasized OVERALL TOTAL row. Empty results still show a zero overall total; branch subtotals represent branches with matching sales.

### Detail

- Verification date.
- Manual receipt number.
- Branch.
- Customer or Guest.
- Salesperson.
- Authenticated encoder.
- Source.
- Units/items.
- Discount.
- Final amount.
- Verification status.

Salesperson output is transaction attribution, not ranking, commission, or Payroll reporting.

## 2. Inventory Summary

### Filters

- Authorized active branch (Stock Room excluded), defaulting to the first by name/ID. Explicit All Branches compares the full authorized active branch set; there is no arbitrary branch-subset picker.
- Product item code/name.
- Category.
- Brand.
- Product status.
- Positive available stock is an invariant, not an optional stock-status filter. The former `stockStatus` parameter is no longer supported and API requests containing it are rejected.

### Summary and Detail

- All product statuses remain included by default; `productStatus` explicitly narrows the snapshot. Available is a quantity calculation, not a claim that an inactive product can be sold.
- Rows are grouped once per product. A product must have positive availability at one or more selected branches. Missing, zero, or negative balances contribute zero available units; products with no positive contribution are omitted. A negative balance does not cancel another branch's positive stock or imply transferable stock.
- Single-branch UI columns are Code, Product, Category, Brand, Available. With multiple effective branches, the UI shows those product fields, one available column per effective branch, and Total Available. A zero comparison cell means no positive stock there, not that the product is excluded from other branches.
- UI displays 25 products per page, resets pagination when applied filters change, and keeps horizontal table overflow for branch comparison. Metrics and table footer totals always cover the entire filtered set, not the page. JSON returns all grouped rows; pagination is display-only, with no `page`/`pageSize` API parameters.
- PDF exports the complete filtered product set, never the current page. Comparison PDFs show per-product totals followed by one fixed-width table section per branch, including zero cells and branch totals. Branch names repeat with continued table headers; additional branches add sections rather than shrinking columns or overflowing horizontally. Single-branch exports only need the product/available table.
- `available = onHand - reserved - quarantined`; Stock Room/warehouses and in-transit stock are excluded. On-hand/reserved/quarantined quantities, reorder, shortage, suggested reorder, and cost/value are not report outputs.
- DTO rows are `{ id, productId, itemCode, product, category, brand, productStatus, available, availableByLocation }`; `id` is the product ID, `availableByLocation` maps every effective branch ID to its nonnegative contribution, and `available` is their sum. The former row-level `locationId`, `branch`, and `stockStatus` are removed. `effectiveScope` supplies ordered branch IDs/labels, and `branchTotals: [{ locationId, available }]` follows that order.
- Summary: `productCount` is grouped row count, `locationCount` counts branches in scope even when no products match, and `available` sums all filtered rows. PDF requests from a default-branch result send the resolved branch ID explicitly so that export does not silently select a different default; the underlying data remains live.

## 3. Returns & Warranty

### Filters

- Case date from/to.
- Authorized branch/location.
- Type: Backjob, Customer Warranty, or Supplier Claim.
- Status and resolution.
- Customer, Supplier, Product, Salesperson, or Installer where applicable.

### Summary and Detail

- Total, open, completed, and overdue cases.
- Counts by type, status, branch, and resolution.
- Quarantined quantity represented by filtered cases.
- Recorded supplier refund/credit amounts, clearly labeled as claim tracking rather than ledger totals.
- Recorded CHARGEABLE Backjob amounts are separate from supplier refunds/credits. Each row exposes `backjobChargeAmount: number | null`: the persisted `Backjob.chargeableAmount` for CHARGEABLE coverage (including a recorded zero), otherwise `null`/Not applicable. `totals.backjobChargeAmount` sums these amounts once per filtered case. UI/PDF summaries and detail label them as recorded Backjob charges, not collected payments, verified Sales revenue, or ledger totals. No sales query, percentage, receipt, or payment is changed or created. Cancelled/rejected cases remain included unless filtered out, just like other recorded case amounts; this is not a collectible balance.
- Case/reference number, original sale/receiving reference, customer/supplier, product/quantity, assigned personnel, status, resolution, target/overdue dates, and linked case.

### Multi-Item Backjobs

Reports select `Backjob.items` ordered by `position` ascending and include every stored `productItemCode`/`productName` in a semicolon-separated product summary. Entity search matches that complete summary case-insensitively, including later items' codes/names. The report does not flatten items into separate case rows or append the scalar first-item snapshot when item rows exist: case counts, breakdowns, and the recorded charge remain once per case.

For persisted cases with no item rows, use one fallback snapshot from `affectedProductItemCode` and `affectedProductName`, with `legacyProductDescription` then "Not recorded" as name fallbacks, matching the Backjob service's legacy handling. There is no fallback to a live catalog name that could overwrite historical snapshots.

`BackjobItem` records an original line reference, product snapshots, and position, not affected-unit quantities. Returns & Warranty `quantity` is now `number | null`; Backjobs always return `null`, shown as "Not recorded" in UI/PDF. Do not infer quantity from the number of selected original lines, sold quantity, or planned/consumed replacement parts. Customer Warranty and Supplier Claim quantities retain their recorded numeric semantics. Backjob service/contracts and Prisma are read-only dependencies of this report integration and were not edited here. Runtime requires the authored `BackjobItem` table and a matching generated Prisma Client; neither migration application nor client generation was performed in this turn.

## Acceptance Criteria

1. Reports page and APIs independently enforce view/export capability and effective location scope.
2. The default Sales Report covers the complete current Manila month of verification dates; omitted To follows the selected From month and explicit custom To remains unchanged.
3. Sales totals contain only verified, non-voided sales and are not truncated by display limits.
4. Sales branch totals reconcile exactly to the authorized grand total.
5. Accounting queues and open-order lists are absent from Reports.
6. Inventory outputs use positive contributions from `available = onHand - reserved - quarantined`, one grouped row per product; unset scope defaults to one authorized active branch and explicit All compares all eligible branches.
7. Inventory Summary is branch-only available stock at present; Returns/Warranty honors selected case dates. Retired report types are absent from options/contracts/export dispatch and rejected by the API without changing operational inventory history.
8. Each PDF matches the selected report, filters, scope, and full aggregate totals.
9. No commission, staff ranking, Payroll, general-ledger, or saved-report behavior is implied.
10. Editing any filter or resetting it does not change report rows/totals/PDF parameters until Apply Filters; independent option requests may run while edits are pending.
11. Inventory shows 25 products per page, but totals and readable branch-section PDFs retain the entire filtered set.
12. Recorded CHARGEABLE Backjob amounts appear in UI/PDF detail and summaries without entering supplier totals or Sales revenue. Sales '% of grand total' behavior is unchanged.
13. Multi-item Backjobs list/search every original snapshot in stored position order, fall back to singular snapshots only without item rows, and remain one case with one charge and no invented affected-unit quantity.

## Verification Limit

This revision is source-only. Existing report assertions were updated for positive-only grouped inventory, branch contributions, unset versus explicit All parameters, ordered Backjob snapshot projection, legacy fallback, and absent affected-unit quantities. A mocked report-service assertion covers later-item code/name search and one case/one charge. None were executed. No tests, build, lint, typecheck, browser/PDF rendering, verification commands, migrations, generation, or server restart were performed. This Reports integration authors no schema or migrations, but reading `Backjob.items` requires the separately authored BackjobItem database/client changes. Large-dataset memory/response size, PDF page counts, and runtime multi-item behavior remain unverified.
